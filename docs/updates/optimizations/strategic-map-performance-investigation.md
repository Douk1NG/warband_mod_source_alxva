# Strategic Map Performance Investigation

## Current status

No source-code performance change has been made. The branch `optimizations` is based at `227583c` (`origin/master`); the source working tree contains only this investigation note. Static source audit, installed-resource inspection, and the earlier asset/Ctrl+T tests are recorded below. The asset remap A/Bs did not isolate a major party-icon or flag-mesh cost, and the Ctrl+T effect remains unverified. A newer same-view probe used Windows performance counters for three 10-second blocks in each state: paused averaged 109.06% process CPU and 41.36% Intel GPU 3D; running averaged 108.88% CPU and 42.17% GPU. This points to a substantial baseline cost that persists while paused, but does not identify the responsible engine or mod path. Two reversible installed test modules remain prepared with copied saves; no original assets, saves, or source code were changed. The investigation remains open pending matched Native and visible-party tests.

## Test procedure

Use one save and keep the game version, resolution, zoom, map location, weather/time, camera position, and background applications fixed. Let the map settle before each sample. Capture a 60-second sample three times per condition, recording average FPS and (if available) 1% low or frametime, per-logical-core CPU use, GPU use, and party counts. Toggle only the stated variable between paired samples. For input tests, measure during the same-duration camera movement and compare idle separately. First record the live launcher's Max Frame Rate, VSync, window/full-screen mode, and game counter. The local profile currently has a 60 FPS cap, so perform one paired set with the current cap and a separate paired set with the cap raised to 120; keep each set internally identical. This determines whether the cap masks headroom or whether the reported 100 FPS battle reading came from another profile/counter.

### First pass with the in-game counter

The player only needs to open Warband, load the usual save, and leave it on the strategic map. `show_framerate = 1` is already set in the standard local profile. For a quick pilot, pause time and hold map position/zoom fixed; the observer captures three counter values about 10 seconds apart per visibility state, and the player presses Ctrl+T only when asked. This screens for a large effect without external tools. If the pilot difference exceeds the natural spread, confirm with the full protocol: three 60-second intervals per state, sampling the counter every 5 seconds, alternating A/B order. If the counter is hard to read, use a screenshot; do not switch windows while a timed interval is running. Note whether the counter is capped at 60. CPU/GPU use, camera input, and the paused/running comparison can follow if the Ctrl+T pair shows a consistent change.

### Discriminating experiment sequence

For formal comparisons, use three 60-second runs per condition, record the counter every 5 seconds, and alternate order where practical. Keep one save, view/zoom, resolution, launcher profile, background applications and cap fixed. The quick three-read pilot is only for screening a large effect.

## Source audit findings

- `source/simple_triggers/scout_ai.py` scans parties every 0.2 in-game hours, then processes only `spt_scout` parties.
- `source/simple_triggers/zaitenko_reinforcements.py` scans parties every 0.2 in-game hours, then processes only reinforcement parties in towns.
- `source/simple_triggers/process_messengers.py` scans parties every 0.5 in-game hours and performs distance checks for messenger parties.
- `source/simple_triggers/recruiter_ai.py` scans parties every 0.5 in-game hours; active recruiters may scan villages and compute distances.
- `source/simple_triggers/cache_party_strengths.py` scans hero troops every 0.5 in-game hours, but its expensive center search is nested under an active retreating-party condition.
- `source/simple_triggers/rebellion_troop_removal.py` scans hero troops every 0.1 in-game hours and tests party attachment/current center. Its name/comments do not establish that it removes troops; its active body attaches parties and transfers prisoners.
- `source/simple_triggers/lord_political_calculations.py` runs every 0.5 in-game hours. It advances `$g_lord_long_term_count` and processes up to two troop IDs per tick (the second pass maps the same active-NPC index into the kingdom-lady range). For each valid troop, it unconditionally scans `centers_begin..centers_end` to tally owned fiefs; the constants cover towns, castles and villages. More scans over walled centers/heroes, and relation calculations, are gated behind specific lord/political states. This is a definite repeated simulation workload, but its in-game-hour schedule and lack of runtime profiling mean its FPS contribution is unknown.
- `source/simple_triggers/center_alarms.py` runs every 0.5 in-game hours. ## Follow-up: KCT load restore trigger was the regression

The user later bisected source revisions and isolated a KCT load restoration simple trigger introduced after `30758b2f66146b123819ac53a22c14ab6e8b32cf`. Runtime A/B evidence on the same revision showed frame rate dropping to 47 FPS with the trigger registered and returning to a stable 60 FPS when its registration was removed. A later revision with the trigger active measured 46–56 FPS; earlier tested revisions were stable at 60 FPS. This overrides the earlier conclusion above that no trigger-frequency change was justified.

Root cause: the trigger interval is `0`, so Warband evaluates its operation block every frame. The block was intended as load restoration, but had no one-time guard. Each evaluation iterated the custom troop range and preset troops and called `script_kct_replace_custom_troop_with_dummy`; that script refreshes names, copies attributes/skills/proficiencies, copies and sorts inventory, equips items, and reapplies class. It also ran native guard restoration, gender reapplication, and save migrations on every frame. This work is expensive and unrelated to drawing the map, so a visual inspection of map meshes or textures would not have identified it. The decisive evidence was revision bisecting plus disabling this one trigger while keeping the rest of the build the same.

The current fix gates the interval-zero trigger with the runtime class of `trp_kct_template_slot_0_meta`, an unused KCT template metadata troop. The trigger exits unless that class differs from `grc_cavalry`, performs restoration/migration once, then sets the marker class to cavalry. KCT documents troop class as a runtime value reset to infantry on every load; template data itself lives in troop slots. This avoids adding persistent marker slots or changing saved template data. Regression check: `tests/test_kct_load_restore_trigger.py`. Initial compile completed successfully; the game A/B and save-load verification remain outstanding.

Static audit of the other interval-zero simple triggers found:

- `custom_troops_simple_triggers.py` has a large fix block, but its `$g_cstm_save_fix_applied_5` guard makes the array rebuild and table writes one-time per save.
- `notification_menus` exits immediately when its queue is empty; work scales with pending notifications.
- `manage_inventory_trigger` polls a key and opens the UI only on input; `auto_menu` checks pending state and performs actions only when requested/eligible.
- `update_player_icon` performs a small player inventory/state check each frame and only changes the map icon when its computed icon differs.
- `captive_party_relocate` is condition-gated and relocates only while the player is captive and the capturer party is active. `decide_faction_ais` exits unless its recalculation flag is set (its debug branch is also cheat-mode gated).

This audit is scoped to simple triggers at interval zero. It is a static triage, not a proof that no other performance issues exist. The broad lesson is to review trigger frequency and guard placement before judging code by how suspicious it looks: a one-time intent in comments does not make an interval-zero operation one-time. For new load migrations, ensure an explicit per-load completion gate; for runtime verification, compare the same build with only the suspected trigger enabled/disabled and separately verify that a fresh load reruns the restoration.

### What the interval-zero block touches on each invocation

On a campaign load that reaches the trigger, it runs once per frame until the new guard is satisfied. For the generic CSTM range, it invokes the restore script for each troop with a positive `cstm_slot_troop_dummy` link. For presets 4–8 it walks every unit in both skins, sets real/dummy troop types, rewrites `cstm_slot_troop_dummy` and `cstm_slot_troop_custom_troop`, calls the restore script for linked real troops, and rewrites `cstm_slot_troop_base_troop` for each upgrade child. Presets 1–3 are included in the generic CSTM range when their dummy links exist.

For every troop actually restored, `script_kct_replace_custom_troop_with_dummy` refreshes singular/plural names; resets and recopies 4 attributes, 42 skills and 7 proficiencies from dummy to real; clears/copies inventory entries and modifiers up to source capacity; sorts and equips the real troop; reads `cstm_slot_troop_class_override` (slot 533); then changes runtime classes on the real and dummy troops. Subsequent per-frame calls repeat these writes even when source and destination already match. The separate block rechecks native faction guard slots, re-applies persisted gender flips (including troop type and appearance), tests/seeds the template metadata slots, and runs the guarded legacy migration. Thus the dominant repeated work is the per-troop reset/copy/equip/class path; migration idempotence alone did not protect the trigger body.

The new runtime marker check prevents all of those loops and writes from running after the first successful pass, while leaving one restoration pass per load. This mechanistic prediction is falsifiable: with the patched trigger enabled, FPS should return to the prior 60 FPS baseline, and reloading a save with edited custom troops should still restore their stats, equipment, names, gender and class. If either fails, the marker assumption or restoration order is wrong and the patch must be revised.

### Estimated repeated volume from source ranges

At `e848fa6`, the legacy CSTM range contains 60 real troops: preset sizes are 7 + 11 + 12 troops per skin, across two skins. The original KCT extension also visits 22 preset-4 nodes per skin (44 more restore candidates). So the unguarded trigger could call the full restore script up to 104 times per frame if those troops have dummy links. Each call resets and copies 4 attributes, 42 skills and 7 proficiencies (two passes over those fields), then copies the source inventory capacity and performs sort/equip/class work. This is an upper bound; the actual call count is the number of positive dummy links.

Descendants expanded the KCT preset block: presets 4–8 contain 56 nodes total per skin, or 112 additional restore candidates. The current descendant can therefore reach up to 172 full restore calls per frame (60 legacy range + 112 KCT nodes), again bounded by valid dummy links. The `troop_set_type` writes, dummy-link writes (slots 500/501), upgrade-base writes (slot 502), and calls to native guard/gender/migration routines are also repeated in the unguarded version. User FPS readings are the evidence that this repeated CPU workload materially affected the map; source counts explain the mechanism but do not replace the pending patched-build runtime check.
